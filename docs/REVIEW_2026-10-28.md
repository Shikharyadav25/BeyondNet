# Review of the supplied Claude assessment

Reviewed against payment-only commit `be270b2` (mobile 1.4.3). The supplied review is useful, but describes an older tree containing Campus and a standalone gateway. Those components are absent from the current checkout. Changes below form mobile 1.4.4/build 18 and its matching bank source.

## Findings applied

| Finding | Verification and change |
| --- | --- |
| Transient database failure reported as invalid payment | Confirmed: `ingest` caught the device lookup inside input validation. Database access now sits outside that catch and produces a retryable server error. A fault-injection test verifies a failed read, HTTP 500 classification, successful retry of the same authorization and one debit. A mobile test verifies that 500 retains the original queued packet and retries its same ID. |
| Routing mismatch can poison receipt delivery | Confirmed: Java accepted duplicate/empty path entries and did not validate optional trail history. Java, Dart and the independent Python oracle now agree on uniqueness, entry length, trail length and hop constraints. A verified replay also refreshes invalid legacy receipt envelopes while retaining the saved financial outcome. |
| One invalid receipt blocks HTTP inbox progress | Confirmed. HTTP and live batches now share per-entry handling: malformed, expired or unverifiable entries are logged and skipped. Valid entries still require signature verification before a financial update. Storage quota and database failures propagate and preserve the cursor; they are not treated as malformed data. Tests exercise malformed entries ahead of a valid receipt, disk/write failure, quota exhaustion, recovery and cursor resumption. |
| Mailbox capability overwrite | Confirmed. An additive `mailbox_claims` table permanently binds each capability to a sender/payment pair. Both claims occur in the settlement transaction; a conflicting new payment rolls back with 409. Cleanup of expiring delivery rows does not release ownership. Existing decisions and SQLite imports backfill claims. Ambiguous historical capabilities stay reserved; refreshed device-inbox delivery can still recover their original signed outcomes without overwriting another mailbox. |
| Mailbox validation inconsistent | Confirmed format gap. Bank instructions, packet readers and Python now require hexadecimal capabilities. Existing 32–100 character hex capabilities remain valid; new app capabilities continue using 48 lowercase hex characters. Requiring exactly 48 would unnecessarily reject valid older authorizations. Mailbox identity remains case-sensitive, as before. |
| Recipient sees sender PIN/lock reasons | Confirmed. Newly generated and refreshed recipient receipts give a generic rejection reason. The sender and local bank operator retain the actionable detail. This does not retract detailed ciphertext already issued by older releases. |
| Missing-account login skips expensive password work | Confirmed. Unknown accounts now perform the same password-hash operation before returning the same generic failure. This removes the obvious skipped-work difference; it is not a constant-time network-login guarantee. |
| Raw tokens accepted without Bearer scheme | Confirmed. HTTP session/operator authorization now requires a nonempty Bearer token with no embedded whitespace. Scheme spelling is case-insensitive. Existing app/console clients already send this scheme; WebSocket authentication still wraps its token in the required scheme internally. |
| Rate-limit cleanup scans every bucket per request | Confirmed. Buckets now remain ordered by their last accepted attempt, allowing expired-prefix cleanup rather than a full scan on every request. Rejecting an attempt does not move its bucket or prolong its window. Existing limits and the bounded fail-closed capacity are retained. |
| Python canonical sorting differs for supplementary keys | Confirmed for hypothetical non-ASCII object keys; current protocol field names are ASCII. The test oracle now recursively follows the existing Java/Dart UTF-16 key ordering. Matching tests in all three languages protect this boundary without changing deployed cryptographic bytes. |

The mailbox ownership migration is additive and transactional. It neither clears payment history nor changes financial idempotency, balances, enrolled device keys or bank trust. The bank must be rebuilt/restarted from this release to activate its fixes.

## Findings retained as design work

| Suggestion | Decision |
| --- | --- |
| Replace global advisory lock with row locks and relative updates | Current balance writes are protected by the PostgreSQL transaction lock, including across bank instances. The supplied observation is a scalability dependency, not evidence of an existing lost update under this locking scheme. Keep the lock and existing concurrency tests. A future change needs deterministic account-lock ordering, PIN/top-up/device consistency, migration and contention benchmarks together. |
| Notify only affected WebSocket clients | Valid performance concern: commit notifications currently queue all connected clients. Work is coalesced, clients are capped and periodic recovery exists, but these do not remove the fanout cost. Defer targeted account/device event delivery until its authorization, revocation and missed-event behavior are tested under load. |
| 10,000-key limiter capacity and victim account throttling | Valid denial-of-service tradeoffs remain. Evicting active counters or removing account throttling would weaken brute-force controls. The cleanup cost is fixed; distributed admission control, challenges and account recovery require a separate policy. No distributed-flood resistance is claimed. |
| Separate management port | Valid deployment hardening. The bank binds loopback by default, requires the operator token, and rejects dashboard access carrying tunnel headers. That boundary assumes a correctly configured HTTP tunnel. Raw TCP tunnels or proxies stripping those headers are unsupported; do not treat header checks alone as management-network isolation. A separate management listener needs coordinated console, launcher and deployment changes. |
| Production signing key and removal of archived APKs | A production distribution/signing plan is needed. Retain the existing demo signing identity to allow upgrades that preserve enrollment keys and pending payments. Do not rewrite Git history or remove historical artifacts as part of a reliability patch. Only the README's latest release should be used for current tests. |
| Migrate canonical JSON to JCS | A protocol migration requires versioning and cross-language vectors. Replacing canonicalization silently would invalidate queued signatures, hashes and ciphertext. The verified oracle ordering mismatch is fixed within the existing integer-only wire format. No JCS compliance is claimed. |
| DTOs, service decomposition and schema migration framework | Reasonable maintainability improvements. No supplied evidence requires a wholesale rewrite to deliver these fixes. The ownership table uses the existing additive schema mechanism and an explicit one-time backfill marker; a versioned migration framework remains future infrastructure work. |
| `db.read` used for autocommit DELETEs; test utilities on database class | Naming/test-boundary cleanup is reasonable. These connections use normal JDBC autocommit, so the method name alone does not prevent DELETEs from committing. Production schema deletion remains guarded to `test_` namespaces. |
| Broad exception handling/logging | The confirmed payment/DB misclassification is fixed. Unexpected bank failures already produce generic 500 responses and log the exception class. Avoid logging request bodies, encrypted instructions, PIN input or credentials while adding diagnostics. |
| Legacy identifiers | `com.offlinekaro`, `KARO_DATA_DIR`, the old SQLite name and the box-domain string are compatibility identifiers. Renaming them blindly would change app installation identity, data lookup or cryptographic derivation. Keep them until a migration explicitly handles each boundary. |

## Findings that do not match the current checkout

| Supplied observation | Current state |
| --- | --- |
| Standalone gateway `DurableQueue` and `BankUplink` | These components are absent. The current gateway is the phone engine, with packet cleanup, status-aware retry, explicit custody and bank receipt recovery. Retention and storage limits still need device acceptance under sustained traffic; no standalone gateway fix was applied. |
| Campus key storage, proxy buckets, controller exceptions and Windows POSIX handling | Campus was removed from the product. Do not reintroduce it to address an obsolete review. |
| Root Maven aggregator lacks backend module | There is no root `pom.xml` in this checkout. Supported commands select `backend/pom.xml` directly. |
| README 1.3.6 versus pubspec 1.4.0 | Stale review snapshot. At the review base both describe 1.4.3/build 17; this patch updates both to 1.4.4/build 18. The bank's retained `bank-1.3.3.jar` name is documented separately from the source release. |

Routing path/trail/hop fields remain unauthenticated delivery hints. Their validation prevents malformed history and honest-peer loops; a malicious enrolled relay can still reset or drop hints and deny delivery. The signed payment body, device identity, amount, expiry and bank idempotency protect financial authorization, not guaranteed radio delivery. This patch does not claim cryptographic hop enforcement or production readiness.

See [1.4.4 release validation](RELEASE_1.4.4.md) for executed checks, artifact identity and physical-test limits.
