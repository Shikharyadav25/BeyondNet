# Security suggestions: assessment and implementation plan

Reviewed against mobile 1.3.3 / Java bank 1.3.3. This update is mobile 1.3.4 (build 11); the bank remains 1.3.3. This is a demonstration with simulated funds, not a certified payment system.

## Immediate plan and implemented change

1. Inspect the actual command authentication, routing and persistence paths.
2. Close the restart replay gap without changing enrolled keys or wire formats.
3. Upgrade SQLite in place; test concurrent replay, restart, skew, expiry, limits and migrations.
4. Run the mobile regression suite and static analysis, build the update APK, verify its signing identity, and package source without private data.

The old receiver remembered request IDs only in memory for 120 seconds from receipt. A restart forgot those IDs; a request dated up to 120 seconds ahead could also remain acceptable after its entry disappeared. The new `LocalStore.claimRpc` transaction persists `(authenticated peer device ID, request ID)` until the signed timestamp plus 120 seconds, inclusive. Signature, certificate and timestamp validation precede the claim; command execution follows its commit. Concurrent copies therefore cannot execute twice. A failed command consumes its request ID; a retry uses a fresh signed request, as the existing sync code already does. Financial packet IDs and bank idempotency remain unchanged.

Expired rows are removed during admission. A peer may hold 256 live claims; the database allows 4,096 globally. It fails closed at capacity rather than evicting active protection. This limits storage, not signature-verification CPU or radio denial of service. A persistent clock watermark rejects requests after a backward clock adjustment until the clock catches up; enable automatic date/time if that occurs. Database restoration/rollback or a compromised phone remains outside this protection. Existing v1/v2/v3 databases upgrade to v4 without deleting history or queued payments.

## Disposition of the suggestions

| Suggestion | Decision and next implementation steps |
| --- | --- |
| HPKE envelope | Valuable protocol migration; not replaced in this patch. The existing X25519/HKDF/AES-GCM box is not RFC 9180 HPKE. Select maintained Java and Dart/native implementations supporting the same suite, verify official vectors, define explicit version and suite IDs, bind bank identity and envelope context, add dual-read support at bank first, advertise supported versions, then update senders. Retain old decryption keys and decoders while pending receipts remain recoverable. Never silently reinterpret a v2 packet. |
| Hardware-backed signing | Valuable, but requires native Android APIs and certificate/signature versioning. Separate user-authenticated payment signing from unattended relay-session signing so screen-off forwarding does not trigger a PIN prompt. Verify attestation on the bank with freshness, chain and revocation checks; inspect actual security level rather than assuming StrongBox. Define a visible software fallback and device replacement/recovery flow. Existing Ed25519 keys cannot simply be relabelled P-256. Test supported and unsupported Android 10+ devices before switching enrollment. |
| Encrypted, replay-protected peer sessions | Restart-persistent request protection implemented now. Session confidentiality remains future work: negotiated authenticated ephemeral key agreement, bind both certificates, challenges, roles and version into the transcript, derive separate directional keys, enforce sequence counters and replay windows, and rekey with fresh session IDs after restart. Require explicit compatibility policy to avoid silent downgrade. Receipts and commands have distinct roles; new protocol should bind responses to peer identity as well as request ID. |
| Offline revocation snapshots | Useful next protocol addition. Persist a monotonically increasing bank sequence in PostgreSQL; sign mesh ID, sequence, issued/expiry timestamps and revoked device IDs. Gateways fetch; peers gossip with size limits. Verify bank signature before storing, reject rollback, persist the highest sequence and quarantine revoked peers. Define stale-snapshot behavior explicitly: an isolated phone cannot learn new revocations immediately. Test tampering, stale state, rollback, bank restart and disconnected reconnection. Bank already rejects revoked senders; peers currently may trust their unexpired certificates. |
| At-rest database encryption / bank KMS | Useful for a serious pilot. Phone queue currently stores encrypted financial envelopes but plaintext history, identity and routing metadata. Introduce SQLCipher with an Android-protected random key, migrate via verified temporary database and atomic switch, and test low storage, process death, backup exclusion and missing-key recovery. KMS/HSM requires an operator-selected provider and compatible signing/decryption interfaces, latency and cost decisions. Do not regenerate bank keys: that changes trust and makes pending ciphertext unreadable. Design key IDs and overlapping verification/decryption retention before rotation. |
| Offline risk, invoices, refunds | Valuable product work, not safely implied by a routing field. Define approved limits and their UI; enforce bank-side amount/velocity/exposure limits atomically alongside duplicate and balance checks. A malicious sender can falsely label a transaction online, so route claims cannot exempt it. Offline phone reservations improve UX but do not prove available funds across devices. Signed invoices need merchant identity, amount, expiry and single-use rules. Cancellation races with settlement; refunds must be separate idempotent ledger entries, never deletion of the original payment. |
| Gateway-aware Spray and Focus | Keep existing routing until simulation and physical evidence support replacement. Current implementation already prefers online peers, retains custody copies, caps fanout/hops, avoids loops and sorts outgoing work by receipt lane then expiry. Proposed numeric weights are hypotheses, not validated settings. A signature proves who claimed reachability, battery or capacity—not that the claim is true. Require recent verifiable bank evidence, score decay and exploration for cold-start peers. |

## Routing research plan and acceptance gates

Build a seeded encounter-event simulator comparing current routing with the proposed score policy on chains, intermittent gateways, disconnected partitions, dense loops and misleading gateway claims. Measure delivery before 600 seconds, receipt return, transmissions, energy proxy, fairness and queue pressure. A strict “only forward to a higher score” rule can deadlock a chain of equally unknown offline devices; preserve exploration and direct-gateway priority.

Copy tokens cannot be exactly conserved by just halving an integer on send: lost acknowledgments and sender crashes create ambiguity. Specify persistent transfer IDs and debit/commit/recovery states, distinguish retained archival copies from forwarding permission, and test every interruption point. Malicious peers can still violate copy budgets; those budgets must never authorize money. Compare delivery rates and traffic over many seeds before enabling an opt-in versioned policy. Then test mixed APK versions on at least five physical Android models, screen locked and battery saver enabled. No such simulator or new scoring algorithm is claimed in this release.

## Audit scope and remaining limits

Automated checks cover production signing/framing/storage/routing paths via the existing simulated chain suite plus new persistent-replay regressions. Physical Bluetooth range, vendor battery restrictions, and radio performance require devices. This patch does not provide HPKE, hardware-backed payment signatures, encrypted BLE metadata, offline revocation gossip, SQLCipher, HSM/KMS, refunds or production certification. Payment TTL remains 600 seconds; pending outcomes are retained for bank reconciliation, not locally declared successful or cancelled without a bank outcome.

Install 1.3.4 over the existing app; do not uninstall or clear storage. Bank URL, trust fingerprint and enrolled identities are unchanged; this patch needs no bank restart. Old APKs can communicate with updated phones, but old receivers retain their replay gap until updated.
